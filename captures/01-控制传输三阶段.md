# 01 · 控制传输三阶段与 DATA0/DATA1 规则（教学样本）

> **⚠️ 诚实声明**：本文包序列为**基于 USB 2.0 规范 §5.5/§8.5.3 重构的教学样本**，不是真实抓包。
> 所有 CRC 为按规范算法对文中负载实算（脚本 [`../tools/_usbcalc.py`](../tools/_usbcalc.py)）；
> 地址、帧号等为示意值。真实抓包获取途径见 [README](README.md)（Wireshark 样例页 /
> 自抓 usbmon·USBPcap / USB-IF 合规 trace）。
> 样本设备与 [00-全速枚举逐包标注.md](00-全速枚举逐包标注.md) 同一只鼠标（地址 5、EP0 64 字节）。

## 1. 三阶段骨架

```
① Setup 阶段  : SETUP + DATA0(8字节请求) + ACK        ← 恒 DATA0, 恒 8 字节
② Data 阶段   : (可选) DATA1 起步, 逐包交替 DATA0/1   ← 方向由 wLength/bmRequestType 决定
③ Status 阶段 : 方向反转的一次 ZLP 事务               ← 数据为 IN 时用 OUT 收尾, 反之亦然
```

**DATA0/DATA1 三条铁律**（记住就能看懂所有控制 trace）：

| 阶段 | 规则 | 为什么 |
|---|---|---|
| Setup | **恒 DATA0**，设备必须 ACK | 请求只有一包，无 toggle 需求；"必须接受"保证每次传输从已知状态开始 |
| Data | **从 DATA1 起步**，成功一包翻转一次 | 接收方靠 toggle 识别"新数据还是旧包重放"；从 DATA1 起步保证与 Setup 阶段的可区分性 |
| Status | **恒 DATA1**（ZLP） | 一包定成败，无 toggle；重传时仍是 DATA1，接收方不会误判为新数据 |

**状态阶段方向**：数据阶段是 IN（设备→主机）→ 状态阶段用 **OUT**（主机再发最后一拍确认）；
数据阶段是 OUT 或没有数据阶段 → 状态阶段用 **IN**（设备发 ZLP 表"办完了"）。

## 2. 案例：SET_CONFIGURATION(1) —— 无数据阶段的控制写

SET_CONFIGURATION 是枚举最后一步，wLength=0 → **两阶段传输**：Setup + Status。

```text
━━━ ① Setup 阶段 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[SYNC] 2D 05 D0      ; SETUP 令牌: ADDR=5, ENDP=0（CRC5 实算）
[SYNC] C3 00 09 01 00 00 00 00 00 27 25
       │  └────────── 8 字节请求:
       │     00 = bmRequestType(OUT/标准/设备)
       │     09 = bRequest(SET_CONFIGURATION)
       │     01 00 = wValue = 1（配置值, 小端）
       │     00 00 = wIndex
       │     00 00 = wLength = 0 → 无数据阶段
       └ CRC16 = 27 25（实算）
[SYNC] D2            ; 设备 ACK —— SETUP 必须接受

━━━ ② Data 阶段 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
（不存在: wLength=0）

━━━ ③ Status 阶段（方向反转: 设备→主机报"办完了"）━━━━━
[SYNC] 69 05 D0      ; IN 令牌
[SYNC] 4B 00 00      ; 设备 DATA1 ZLP（恒 DATA1; CRC16 对空负载 = 00 00）
[SYNC] D2            ; 主机 ACK → 传输成功, 设备进入 Configured
```

看懂三个失败变体，才算真懂三阶段：

### 2.1 变体 A：设备暂忙 —— 状态阶段 NAK

状态阶段**允许 NAK**（设备还没处理完）：

```text
[SYNC] 69 05 D0
[SYNC] 5A            ; NAK: "还没办完" —— 主机稍后重试同样的 IN
[SYNC] 69 05 D0      ; 主机重发
[SYNC] 4B 00 00      ; 这次好了: DATA1 ZLP
[SYNC] D2
```

注意：SETUP 阶段设备不能 NAK（规范要求必须接受），拖延只能发生在状态阶段。

### 2.2 变体 B：请求非法 —— STALL

```text
[SYNC] 2D 05 D0
[SYNC] C3 00 09 05 00 00 00 00 00 26 A1   ; 伪造: SET_CONFIGURATION(5), 配置不存在
[SYNC] D2
[SYNC] 69 05 D0      ; 主机照常进入状态阶段
[SYNC] 1E            ; 设备 STALL: "这个请求我办不了"
```

要点：
- 控制 STALL 是**请求级错误**，收到下一个 SETUP 自动清除——这是它与普通端点
  STALL（要 ClearFeature(HALT) 才清）的最大区别；
- STALL 既可以出现在状态阶段（本例），也可以出现在数据阶段（设备读了 wValue 就知道请求非法时）。

### 2.3 变体 C：状态阶段包损坏 —— 自动重传

```text
[SYNC] 69 05 D0
[SYNC] 4B 00 00      ; CRC 坏 → 主机静默丢弃（不发 ACK）
[SYNC] 69 05 D0      ; 设备重发 —— 仍是 DATA1（toggle 只在成功时翻转）
[SYNC] D2
```

这就是"状态阶段恒 DATA1"的意义：重传时接收方不会把它误判为新的一拍。

## 3. 案例：GET_DESCRIPTOR(Configuration) —— 有数据阶段的控制读

数据阶段 IN、且描述符比 EP0 包长长时，能看到 DATA1→DATA0 交替与短包收尾。
以 **wMaxPacketSize0=16 的 LS 鼠标**读 34 字节配置为例（放大 toggle 细节）：

```text
━━━ ① Setup ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[SYNC] 2D 03 50      ; SETUP, ADDR=3（LS 鼠标, 地址示意）, EP0
[SYNC] C3 80 06 00 02 00 00 22 00 B0 F4   ; wLength=34
[SYNC] D2

━━━ ② Data 阶段: DATA1 起步, 交替 ━━━━━━━━━━━━━━━━━━━━
[SYNC] 69 03 50      ; IN
[SYNC] 4B 09 02 22 00 01 01 00 A0 32
         09 04 00 00 01 03 01  AC FB   ; DATA1: 第 1~16 字节（EP0=16 满包, CRC16 实算）
[SYNC] D2
[SYNC] 69 03 50
[SYNC] C3 02 00 09 21 11 01 00 01 22 5B 00
         07 05 81 03 08  0C C0         ; DATA0: 第 17~32 字节（满包, toggle 翻转）
[SYNC] D2
[SYNC] 69 03 50
[SYNC] 4B 00 01  3F 8F                ; DATA1: 第 33~34 字节 —— 短包(<16)=数据阶段结束
[SYNC] D2
━━━ ③ Status: 方向反转（数据是 IN → 收尾用 OUT）━━━━━━
[SYNC] E1 03 50      ; OUT
[SYNC] 4B 00 00      ; 设备 DATA1 ZLP
[SYNC] D2
```

FS 鼠标这 34 字节如果 EP0=64 则一包 DATA1 就完（见 [00](00-全速枚举逐包标注.md) 事务五）；
本例故意用 16 字节 EP0 展示三包交替与短包收尾。规律：
**toggle 只由"成功收发"驱动，与包内容无关；包长不得超过 EP0 上限；短包（<wMaxPacketSize）
提前终止数据阶段**。

## 4. 对照表：四个标准请求的三阶段形态

| 请求 | Setup DATA | Data 阶段 | Status 收尾 |
|---|---|---|---|
| SET_ADDRESS / SET_CONFIGURATION / SET_FEATURE / CLEAR_FEATURE | DATA0 | 无 | IN → DATA1 ZLP → ACK |
| GET_DESCRIPTOR(Device/Config/String) | DATA0 | IN, DATA1 起步交替, 短包/计满结束 | OUT → DATA1 ZLP → ACK |
| GET_STATUS / GET_CONFIGURATION（1~2 字节） | DATA0 | IN, 一包 DATA1 | OUT → DATA1 ZLP → ACK |
| SET_REPORT / SET_IDLE（HID 类写） | DATA0 | OUT, DATA1 起步交替（主机发数据） | IN → DATA1 ZLP → ACK |

通用口诀：**"数据谁发，状态就归对方收"**——数据阶段 IN 则状态 OUT，数据阶段 OUT（或没有）则状态 IN。

## 5. 在 Wireshark 里怎么核对这些包

usbmon/USBPcap 是 URB 级，但 Wireshark 会把 Setup 阶段 8 字节解析成字段，过滤器直接验证：

```
usb.transfer_type == 0x02          ; 只看控制传输
usb.setup.bRequest == 0x09         ; 只看 SET_CONFIGURATION
usb.setup.bmRequestType == 0x80    ; 只看标准 IN 请求
usb.endpoint_address == 0          ; 只看端点 0
usb.bDescriptorType == 0x02        ; 配置描述符相关
```

完整过滤器速查见 [`../tools/wireshark_filters.md`](../tools/wireshark_filters.md)。
