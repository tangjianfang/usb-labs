# 02 · 中断 IN 轮询：HID 鼠标报告与 NAK 节拍（教学样本）

> **⚠️ 诚实声明**：本文包序列为**基于 USB 2.0 规范 §5.7 与 HID 1.11 规范重构的教学样本**，
> 不是真实抓包。CRC 按规范算法实算（[`../tools/_usbcalc.py`](../tools/_usbcalc.py)）；
> 帧号、时间戳、报告内容（位移/按键组合）为示意值。真实抓包获取见 [README](README.md)
> （Wireshark 样例页 / usbmon·USBPcap 自抓 / USB-IF 合规 trace）。注意：usbmon/USBPcap
> 抓不到 NAK——NAK 是线级握手，只有硬件分析仪（Beagle/Ellisys/OpenVizsla 等）可见。

**样本设备**：[00](00-全速枚举逐包标注.md) 枚举的那只 FS 鼠标——
EP1 IN 中断端点，`wMaxPacketSize=8`，`bInterval=1`（每 1ms 轮询一次 = 1000 Hz）。
设备内部传感器实际 ~125 Hz 出报告（每 8ms 一次）——**主机轮询快、设备出数慢，
于是线上大部分是 NAK**，这正是本篇要教的东西。

## 1. 中断传输的真实身份：主机保证的轮询

"中断"不是设备打断主机，而是主机**承诺每 ≤bInterval 就来问一次**（IN 令牌）：

```
端点描述符: 07 05 81 03 08 00 01
                     │  ─┬─  └ bInterval = 1 → 每 1 帧一个 IN 事务
                     │   └─── wMaxPacketSize = 8 字节
                     └─────── 0x81 = IN / 端点 1
```

bInterval 语义随速率变化（易错点）：

| 速率/类型 | bInterval 含义 | 鼠标常见值 |
|---|---|---|
| FS/LS 中断 | 帧数（1~255ms，LS 下限 10ms） | 1ms=1000Hz（游戏）/ 8ms=125Hz（办公） |
| HS 中断 | 2^(n-1) 个微帧（125µs~） | 1 → 8000Hz 电竞 |

**低速鼠标上限 100Hz**（bInterval≥10ms）——"1000Hz 回报率"必然是 FS/HS 设备。

## 2. IN 事务的三种命运

```
主机                          设备
 IN 令牌 ────────────────▶  有新报告?
                             ├─ 有 → DATA0/1(报告)  → 主机 ACK   ✓ 成功, toggle 翻转
                             └─ 无 → NAK            （主机下个 interval 再来, 不算错误）
```

三种包一次看全（一个成功的事务 = Token + Data + Handshake）：

```text
[SYNC] 69 85 60      ; IN 令牌: ADDR=5, ENDP=1（CRC5 实算）
[SYNC] C3 01 7F 00 00 00 00 EB FF
       │  └────── 6 字节报告 ──────┘ │  └ CRC16 = EB FF（实算）
       └ DATA0
[SYNC] D2            ; 主机 ACK
```

6 字节鼠标报告（Report 协议，布局与 [00](00-全速枚举逐包标注.md) 附录的 91 字节
报告描述符逐位对应）：

| 字节 | 内容 | 本例值 |
|---|---|---|
| 0 | 按钮位图 bit0左/bit1右/bit2中 + bit3滚轮按下 + bit4~5侧键 | `01` = 左键按下 |
| 1 | X 相对位移（−127~127） | `7F` = +127 计数 |
| 2 | Y 相对位移 | `00` |
| 3 | 垂直滚轮 | `00` |
| 4 | 水平滚轮 (AC Pan) | `00` |
| 5 | bit0~1 侧键 + 填充 | `00` |

## 3. 一段真实形态的轮询流（8 帧时间窗）

设备 8ms 出一份新报告，主机每 1ms 问一次。帧号从 100 开始（**示意值**）：

```text
┌ SOF  A5 64 F8   帧100
│ IN 69 85 60 → DATA0 01 7F 00 00 00 00 (EB FF) → ACK D2   ← 新报告: 左键+X=+127
│   设备: "200 计数的位移一帧装不下, 拆两帧"
├ SOF  A5 65 00   帧101
│ IN 69 85 60 → NAK 5A                                     ← 无新数据, 不是错误
├ SOF  A5 66 40   帧102
│ IN 69 85 60 → NAK 5A
├ SOF  A5 67 B8 … A5 6A 08   帧103~106 —— 连续 NAK（略）
├ SOF  A5 6B F0   帧107
│ IN 69 85 60 → NAK 5A
├ SOF  A5 6C 88   帧108
│ IN 69 85 60 → DATA1 01 49 00 00 00 00 (23 FB) → ACK D2   ← 新报告: X=+73 (127+73=200)
├ SOF  A5 6D 70 … A5 73 60   帧109~115 —— NAK ×7（略）
├ SOF  A5 74 18   帧116
│ IN 69 85 60 → DATA0 00 00 00 00 00 00 (FF E4) → ACK D2   ← 释放: 按钮清零, 位移=0
└ SOF  A5 7C 68   帧124
  IN 69 85 60 → DATA1 00 00 00 FF 00 00 (CF D4) → ACK D2   ← 滚轮下滚一格: Wheel=-1(0xFF)
```

### 从这段里读出四条规则

1. **NAK 不翻转 toggle**。数据包 PID 序列是 DATA0 → DATA1 → DATA0 → DATA1，
   中间夹多少 NAK 都不影响——toggle 只在成功收发时翻转；
2. **NAK 不是错误**：不计入错误计数器、不触发重传逻辑，主机下一个 interval 原样再问；
   线级 trace 里"NAK 海洋 + 偶发 DATA"就是中断端点的正常长相；
3. **零位移也发包**：释放按钮时 `00 00 00 00 00 00` 照发——报告是"状态快照"，
   按钮变化必须送达；而纯无变化周期设备可直接 NAK 省带宽；
4. **相对位移拆帧**：+200 超过 8 位上限 127 → 拆成 +127/+73 两帧，由主机累加。

## 4. NAK 密度与带宽账

bInterval=1ms、报告 125Hz 时：每 8 个 IN 事务里 7 个 NAK、1 个 DATA。
一次 IN 事务线上开销（FS）≈ Token 35bit + Data 547bit + ACK 19bit；NAK 事务只有
Token + NAK ≈ 51bit。所以 1000Hz 轮询的 NAK 风暴只吃掉约 5% 帧带宽——
**NAK 很便宜，这才是"轮询式中断"敢开 1000Hz 的底气**。

推论（调参用）：

- 想省电 → 拉大 bInterval（1000Hz→125Hz，NAK 与唤醒延迟一起减少）；
- 上报率瓶颈在设备端缓冲供应：trace 里该端点交付间隔实测 >bInterval，
  说明固件供数不足（双缓冲是解法）；
- 实测方法：`tshark -Y "usb.src==\"1.5.1\"" -T fields -e frame.time_relative`
  （见 [`../tools/wireshark_filters.md`](../tools/wireshark_filters.md)）。

## 5. usbmon 视角（软件抓包看不到 NAK）

软件层同一时段只有这些 URB（1000Hz 提交 → 立即完成）：

```text
# sudo tshark -i usbmon2 -Y "usb.src==\"1.5.1\" || usb.dst==\"1.5.1\""
No. Source   Info
1   1.5.1    URB_INTERRUPT in (6B)   ← 每毫秒一对 submit/complete
2   host     URB_INTERRUPT in        ← complete, 6 字节
…                                   ← NAK 在这里不可见, 表现为 complete 稍晚
```

想看本文的线级 NAK/ACK/DATA0/1，需要硬件分析仪或 OpenVizsla。
